Portainer Setup Guide

Build Portainer from source, run it on Docker Desktop's Kubernetes, give it a real address on the internet, and route every app you deploy after it — automatically, no repeat setup.

Sections 5 Shell bash / zsh Cluster docker-desktop Est. time 45–75 min

Before you start

  • Docker Desktop installed (Mac, Windows, or Linux)
  • A terminal you're comfortable in — Terminal.app or iTerm on macOS, WSL or Git Bash on Windows
  • A local clone of the portainer-suite repository, for section 2
  • A domain name added to a Cloudflare account, for sections 3 and 5
01

Docker Desktop Setup

Docker Desktop is an app that runs a small, self-contained environment on your computer for building and running containers — bundles of an application with everything it needs to run, sealed off from the rest of your machine.

Kubernetes is the layer on top that decides where each container runs, restarts it if it crashes, and keeps a record of everything currently running. Docker Desktop can start a real (if small) one-machine Kubernetes cluster for you, with one click.

Turn on Kubernetes

Open Docker Desktop → the gear icon (Settings) → the Kubernetes tab in the left list → check Enable Kubernetes → Apply & Restart.

This takes a few minutes the first time — Docker Desktop is downloading and starting the Kubernetes components in the background.

Confirm it's actually upterminal

Once Docker Desktop's status bar shows a steady green Kubernetes indicator, check from the terminal:

bash
kubectl config get-contexts
kubectl get nodes
What you should see A context named docker-desktop marked current with a *, and one node called desktop-control-plane with STATUS reading Ready. If the node isn't Ready yet, give it another minute and re-run the second command.
02

Install Portainer

Portainer is a web dashboard for Kubernetes and Docker — it shows you what's running, lets you deploy new things, and manages users and permissions, without needing to memorize terminal commands for everything.

We're building the Enterprise Edition ourselves, straight from the portainer-suite source code, so what ends up running is entirely your own build — nothing downloaded pre-made.

Check your chip typeterminal

Portainer's build needs to know which kind of processor it's compiling for.

bash
uname -m
What you should see arm64 on Apple Silicon Macs — use ARCH=arm64 below. x86_64 on an Intel Mac or a typical Windows/Linux PC — use ARCH=amd64 below instead.

Install the frontend's dependenciesrepo root

From the root of the portainer-suite repository:

bash
pnpm install

Build the Portainer imagepackage/server-ee

Move into the Enterprise Edition package and build it — remember to swap in the architecture from step one:

bash
cd package/server-ee
make build-image ENV=production PLATFORM=linux ARCH=arm64

This compiles the Go server, builds the web interface, and packages both into a Docker image called portainerci/portainer-ee:local. It can take ten minutes or more the first time.

Always set ENV=production

Leave ENV off and the Makefile quietly defaults to a development build. It still runs, but the browser bundle it produces comes out around 100MB, completely unminified. Loading that page looks exactly like it's frozen — it isn't, it's just downloading and parsing a huge file. Setting ENV=production gives you the same app at roughly a tenth of the size.

Hand the image to Kubernetesterminal

Docker Desktop's Kubernetes actually runs inside its own small container (built on the open-source kind project), which keeps a separate image store from your regular docker command. So the image you just built needs to be explicitly copied across:

bash
docker save portainerci/portainer-ee:local | \
  docker exec -i desktop-control-plane ctr -n k8s.io images import -

Describe what to runsave as portainer.yaml

Kubernetes needs four small declarations: a Namespace (a labeled drawer to keep everything for Portainer together), a PersistentVolumeClaim (a slice of disk so Portainer's data survives restarts), a Deployment (the actual instructions for running the Portainer container), and a Service (a stable address other things use to reach it — here, one that's reachable from your own machine).

Save this as portainer.yaml:

yaml
apiVersion: v1
kind: Namespace
metadata:
  name: portainer
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: portainer-sa-clusteradmin
  namespace: portainer
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: portainer-crb-clusteradmin
subjects:
  - kind: ServiceAccount
    name: portainer-sa-clusteradmin
    namespace: portainer
roleRef:
  kind: ClusterRole
  name: cluster-admin
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: portainer
  namespace: portainer
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: portainer
  namespace: portainer
  labels:
    app: portainer
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: portainer
  template:
    metadata:
      labels:
        app: portainer
    spec:
      serviceAccountName: portainer-sa-clusteradmin
      containers:
        - name: portainer
          image: portainerci/portainer-ee:local
          imagePullPolicy: Never
          args:
            - --tunnel-port=30776
          ports:
            - containerPort: 9443
            - containerPort: 9000
            - containerPort: 8000
          volumeMounts:
            - name: data
              mountPath: /data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: portainer
---
apiVersion: v1
kind: Service
metadata:
  name: portainer
  namespace: portainer
spec:
  type: LoadBalancer
  selector:
    app: portainer
  ports:
    - name: https
      port: 9443
      targetPort: 9443
    - name: http
      port: 9000
      targetPort: 9000
    - name: edge
      port: 8000
      targetPort: 8000

Then hand it to the cluster:

bash
kubectl apply -f portainer.yaml

Collect your one-time setup codeterminal

bash
kubectl logs -n portainer -l app=portainer | grep setup_token
What you should see A line like setup_token=0cdbeca0a0db44a9…. Copy the value after the equals sign — you'll paste it in the next step. This code regenerates every time the Portainer pod restarts, so if you come back to this later and it's rejected, just run this command again for a fresh one.

Finish setup in the browser

Open https://localhost:9443. Your browser will warn you about the certificate — that's expected, since Portainer generated its own certificate rather than getting one from a public authority. Click through it (usually Advanced → Proceed). Paste your setup code, choose an admin username and password, and Portainer is now yours to use.

03

Tunnel Portainer

Right now Portainer only answers on your own computer. A Cloudflare Tunnel lets you reach it from anywhere on the internet, under a real domain name — without opening a single port on your router or exposing your home IP address to the world.

A small program called cloudflared runs inside your cluster and calls out to Cloudflare to set up the connection. Nothing ever calls in, so there's nothing to attack from the outside.

Create the tunnel

In Cloudflare's Zero Trust dashboard → Networks → Tunnels → Create a tunnel → choose the Docker connector. Cloudflare shows you a docker run command containing a long token after --token — copy just that token. Don't run the command it gives you; we'll run this inside Kubernetes instead.

Give it a public address

Still on that tunnel's setup screen, add a public hostname:

  • Subdomain: portainer
  • Domain: yourdomain.com — replace this with the domain you actually added to Cloudflare, everywhere it appears from here on
  • Service type: HTTPS
  • URL: portainer.portainer.svc.cluster.local:9443
  • Under TLS settings, enable No TLS Verify — Portainer's certificate is self-signed, so Cloudflare needs to be told not to double-check it for this one internal hop.

Store the token in Kubernetesterminal

Kubernetes Secrets keep sensitive values like this out of any file you might commit or share:

bash
kubectl create secret generic cloudflared-token \
  --namespace portainer \
  --from-literal=token='PASTE_YOUR_TUNNEL_TOKEN_HERE'

Run the tunnel itselfsave as cloudflared.yaml

yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared
  namespace: portainer
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cloudflared
  template:
    metadata:
      labels:
        app: cloudflared
    spec:
      containers:
        - name: cloudflared
          image: cloudflare/cloudflared:latest
          args:
            - tunnel
            - --no-autoupdate
            - run
          env:
            - name: TUNNEL_TOKEN
              valueFrom:
                secretKeyRef:
                  name: cloudflared-token
                  key: token
bash
kubectl apply -f cloudflared.yaml

Verify it made it acrossterminal

bash
kubectl get pods -n portainer -l app=cloudflared
kubectl logs -n portainer -l app=cloudflared | grep -i "registered tunnel"
curl -s https://portainer.yourdomain.com/api/status
What you should see The pod Running, a handful of Registered tunnel connection log lines, and the same little JSON reply ({"Version":"3.0.0-rc1", …}) you'd get hitting localhost:9443 directly — except this time it came in over the open internet.
04

Install Traefik

Once you're running more than one app in the cluster, something needs to look at each incoming request and decide which app it's actually meant for. That's an Ingress controller's job — a traffic router that sits in front of everything. Traefik is the one we'll use.

We'll install it through Portainer's own screen this time, using Helm — think of Helm as an app store for Kubernetes software: point it at a package (a "chart"), and it installs everything that package needs in one go.

Add the Traefik chart repository

In Portainer: your username (top right) → Helm repositories → Add repository → enter:

url
https://traefik.github.io/charts

Open the Helm install screen

Go to your Kubernetes environment → Applications → the Create from code dropdown → Helm chart.

  • Namespace: traefik (create it here)
  • Release name: traefik
  • Helm chart source: the repository you just added
Two charts look almost identical — pick the right one

The chart list will show both traefik and traefik-crds. Choose traefik. traefik-crds only installs some supporting definitions Traefik uses — it has no traffic router inside it at all, and can't move a single request on its own.

Set the values and install

In the values.yaml box on that same screen, paste:

yaml
ingressClass:
  enabled: true
  isDefaultClass: true

This tells the chart to register itself as the cluster's default traffic router, so anything deployed afterward uses it without being told to explicitly. Scroll down to check the manifest preview, then click Install.

Confirm it's the one in chargeterminal

bash
kubectl get ingressclass
What you should see A row named traefik with (default) next to it.
05

Create Subdomain Work

Without this last piece, every new app you deploy would need its own manual entry back in the Cloudflare dashboard before anyone could reach it. A wildcard subdomain — one rule covering anything.yourdomain.com — fixes that permanently in a single step, because Traefik (installed in section 4) is what actually decides which app answers each request. Cloudflare just needs to hand all of them off to Traefik.

Add one wildcard rule to the same tunnel

Back in the tunnel from section 3 → Public Hostname tab → Add a public hostname:

  • Subdomain: *
  • Domain: yourdomain.com
  • Service type: HTTP
  • URL: traefik.traefik.svc.cluster.local:80 — adjust the namespace in the middle if you installed Traefik somewhere other than the traefik namespace in section 4

Save it. That's the entire routing setup — done once, forever.

Check the DNS record actually got created

Cloudflare sometimes skips this one step

Saving a public hostname is supposed to create the matching DNS record automatically — and reliably does for an exact hostname like portainer.yourdomain.com. For wildcard entries specifically, it sometimes quietly doesn't. If subdomains still won't resolve after the steps below, this is almost always why.

The fix: in Cloudflare, go to DNS → Records. Open the record for your exact portainer hostname from section 3 and copy its Target (something ending in .cfargotunnel.com). Then add a new record: Type CNAME, Name *, Target that same value, Proxy status Proxied (orange cloud).

Prove it works end to endterminal

bash
dig +short anything-made-up.yourdomain.com
curl -s http://anything-made-up.yourdomain.com/
What you should see The dig command returns Cloudflare's IP addresses even for a name you made up on the spot — proof the wildcard is live. The curl will come back empty or 404, which is also correct: nothing is actually deployed at that name. Deploy a real app under this domain from here on, and it's reachable immediately — no trip back to Cloudflare required.
